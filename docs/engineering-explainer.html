Engineering explainer · UK visitor visa service agent PoC

英国visitor签证材料准备Agent

这个 PoC 展示一个基于 email / WhatsApp 风格交互的英国访客签材料顾问： 它采访客户、生成个性化材料清单、接收真实附件、抽取字段、做材料质检、 追补失败材料，并在人工复核前生成有证据引用的整案观察。人工顾问确认后， 系统把正确材料和 final report 打包给用户。

1. 这个 PoC 做什么，不做什么

产品范围锁定在 UK Standard Visitor。当前 PoC 的主演示和主要测试采用 探亲访问 + 英国定居亲属 作为 reference scenario，不代表产品只服务探亲客户。 选择这个场景不是因为它最简单，而是因为它能体现顾问价值：客户可能资金刚够、 有英国定居亲属、计划停留较久，需要系统主动识别材料缺口和风险因素。

做 材料准备闭环 intake、清单、附件收集、OCR/文本抽取、规则校验、补件、人工复核、最终交付包。
不做 不提交申请 Home Office 没有第三方提交 API；最终提交仍由申请人或人工顾问在官方服务完成。
边界 观察风险，不预测结果 系统检查材料并提出有证据引用的整案问题；不输出成功率，也不判断申请是否满足要求。
当前实现口径：现场默认 demo 的整案观察由确定性 fallback 生成，便于离线复现； 真实 LLM 可通过 VISA_AGENT_CASE_ANALYSIS_LLM=1 接入 model.analyse_case(...)，但输出只是 candidate observation，仍必须通过引用校验和边界校验。 当前只有 visitor_family_visit 这一套 route 配置和完整测试覆盖，旅游、短期商务等 Standard Visitor 目的还没有各自独立的材料规则和测试夹具。
签证材料业务的错误代价高度不对称：多问一句只是麻烦，漏材料或编造事实可能导致拒签、 费用损失和长期记录。因此核心决策必须可复现、可审计、可关闭失败。

2. 用户体验流程

PoC 的主线不是“聊天”，而是让客户沿着一个稳定的材料交付流程前进。 客户可以用自然语言和邮件附件交互，系统内部仍然用状态机控制下一步。

1. 新客户来信无 case id 的第一封邮件自动创建 case。
2. Intake自然语言提取姓名、国籍、日期、目的、资金等字段。
3. 清单生成根据案情从 YAML 规则映射出必需材料。
4. 材料收集客户用邮件发 PDF、DOCX、图片或文本附件。
5. 质检补件字段提取后跑代码 validator；失败材料要求重发。
6. 整案分析围绕离境、资金、停留模式、担保关系生成有引用的问题。
7. 人工复核通过材料进入 adviser panel，人工 approve 后发最终包。

最终用户交付物

  • visa-final-review-report.pdf：用户阅读的主报告。
  • visa-final-review-report.html：浏览器可读 fallback。
  • 所有 accepted 的原始材料文件。失败材料不会打包，也不会出现在最终报告里。

3. 代码架构

当前实现是一个小而完整的后端：SQLite 做状态源，状态机控制流程，YAML 存规则， 邮件 poller 接真实邮箱，admin panel 承担人工复核关口。

模块责任为什么这样拆
src/state.py 纯函数决定下一步 action：ask slot、request evidence、resupply、deliver、human review。 流程不能靠对话历史或模型记忆，必须同一 case 得到同一下一步。
src/store.py SQLite case、inbound dedupe、outbox、audit、trace、adviser review。 多轮邮件会乱序、重复、跨天；数据库是唯一 case state。
src/email_bridge.py IMAP 拉取邮件、解析线程、保存附件、映射 evidence id、调用 engine。 渠道接入独立于业务逻辑，后续可替换 WhatsApp/其他邮箱。
src/document_extract.py 从 PDF/DOCX/text/image OCR 文本中提取候选字段。 读取材料和判断材料是两件事；读取失败不能假装通过。
src/validate.py 字段存在、姓名匹配、日期关系、跨材料一致性、advisory 检查。 签证材料是否可用由代码判断，不由 LLM 判断。
src/case_analysis.py 构建整案事实上下文，运行确定性观察，并校验可选模型提出的候选观察和引用。 把“顾问式整案关系分析”加入 demo；模型接口是可插拔的，当前 live demo 使用 deterministic fallback。
src/deliver.py 生成内部 adviser review pack、QC、表格答案草稿、cover note draft。 交付物要可复现；模型只允许提供受事实账本约束的 narrative。
admin_panel.py 本地 adviser review UI，approve/follow-up，并发送最终用户包。 PoC 明确保留人工复核，不让 agent 自己签发最终判断。 
email inbox
  -> EmailPoller
  -> Engine.handle_reply / Engine.apply_document
  -> Store(case state + traces)
  -> state.next_action()
  -> deterministic document validators
  -> whole-case fact context
       -> deterministic fallback (current demo)
       -> optional AI candidates (adapter seam)
       -> evidence-reference guard
  -> adviser panel
  -> final package to client

4. 为什么不是纯 agent，也不是纯 workflow

这个项目的核心取舍是：workflow 做主干，AI 只能进入有护栏的能力槽位。 workflow 负责流程、硬规则、事实账本和交付边界；AI 负责理解真实输入、 抽取非结构化材料字段。整案分析已经具备可插拔 AI candidate 接口，但当前 demo 先用确定性 fallback 产出观察，再用同一套引用护栏验证输出。

阶段采用方式原因
新客户输入 / intake AI + schema 客户会把多个事实写在一句话里，也会乱序回答；LLM 适合抽取候选字段。
清单生成 Workflow 材料要求来自配置和规则来源，漏一项成本高，不能让模型临场发挥。
附件字段抽取 OCR/解析器 + 可选 AI fallback 真实 PDF/图片格式复杂，AI 可帮助读非结构化文本，但只产出候选字段。
材料是否通过 Workflow / code validator 姓名、日期、必填字段、跨文件一致性必须可复现。
整案分析 规则 facts + deterministic fallback + optional AI candidate + code guard 当前 demo 稳定展示长停留、资金和国内联系等观察；接入模型后，每条候选仍必须引用 case facts，不能输出结论。
风险诊断 规则 + 允许的问句 可以提示风险因素和追问，但不能输出成功率或充分性结论。
最终交付 Workflow + human gate 系统组包，人工顾问 approve；agent 不对真实 visitor test 做最终判断。
判断标准很简单：输出空间有限、错误不可逆、需要审计的地方用 workflow； 输入混乱、跨材料语义组合、表达需要自然语言且能被引用校验拦住的地方用 AI。

5. AI 交付稳定性：不是提示词，是控制面

PoC 里所有 AI 输出都先经过结构化边界，不能直接写最终 case state 或最终报告。 这里的稳定性不是“模型更聪明”，而是模型失败时系统仍然不编造、不漏件、不静默。

风险控制当前实现
LLM 编造材料要求 规则外置，只有 route registry + versioned rule pack + source id 能定义要求。 config/routes.yaml + config/* rule packs + config/sources.yaml
LLM 输出错误 JSON schema coercion，invalid 字段拒绝；最多一次 repair。 src/ingress.py，trace 写入 ingress_events
模型读不清材料还放行 读取失败转为 blocking failure，要求重发。 Engine.apply_document() 捕获 ModelRefusal
上传顺序导致跨文件漏检 每次上传后重检所有已收材料。 Engine._revalidate_all()
重复邮件重复推进 inbound dedupe key。 inbound table 记录 Message-ID / attachment key
发信失败不可追踪 outbox 先写库，再发送，发送成功后标记。 outbox table + sent_at
生成文本加入客户没提供过的事实 事实账本扫描日期、金额、重要数字。 src/facts.py 的 FactLedger
整案分析变成“签证能不能过”的判断 只允许预定义分析类别；禁止成功率、强弱评分和 sufficiency 语言。 case_analysis.validate_observation()
LLM 提出无依据观察 每条 observation 必须带 evidence_refs，source 必须存在于 facts，上报 value 必须匹配。 case_analysis.build_fact_context() + 引用校验
模型漫无边际挑刺 最多输出少量 adviser 值得追问的问题；默认 5 条以内。 case_analysis.analyse(..., limit=5)

失败策略是 fail closed：不懂的 validator 报错，不可读材料要求补件，LLM 超时保留已接受字段并继续流程， 不让一个模型调用阻断确定性的下一步。

6. 数据、审计和最终包

PoC 用 SQLite，而不是把状态藏在 prompt 或聊天记录里。这样现场演示可以直接解释“数据库现在记了什么”， 也能说明后续生产化该怎么拆表。

表/字段用途
casescase id、stage、slots、evidence 聚合快照。
inbound入站去重，避免重复邮件重复推进。
outbox出站消息审计，避免“以为发了但没发”。
audit业务事件流水：case_created、slot_filled、evidence_recorded、pack_assembled。
ingress_eventsLLM intake 候选、接受、拒绝、repair 和 validation errors。
document_extraction_events材料 OCR 文本、候选字段、接受字段、拒绝字段。
validation_events每条 validator 的 pass/fail 结果。
whole_case_analysis当前在 review pack 中代码生成，不单独落表；生产环境应拆成可采纳/驳回/改写的 adviser workflow。
adviser_reviews人工顾问 approve 或要求 follow-up。

最终交付包如何避免打包错材料

  • 只从 case.outstanding(checklist) 的 satisfied set 取材料。
  • 只附加 blocking failures = 0 且 document_ref 文件存在的原始附件。
  • 失败材料既不作为附件发送，也不出现在用户 final report。
  • 报告里只列 included accepted materials，并匹配真实文件名，方便用户核对。

7. PoC 到生产环境会改变什么

PoC 追求两天内可演示、可解释、稳定闭环。生产环境不是简单“把 demo 部署上去”， 需要在数据保护、权限、可观测性、规则更新和人工责任上补齐。

PoC 当前做法生产化改造
SQLite 存 case 聚合 JSON。 拆成 cases、case_profile、case_evidence、documents、evidence_failures 等表。
附件保存本地磁盘。 对象存储 + 文件 hash + 病毒扫描 + 加密 + 访问审计 + 保留期限。
本地 admin panel 无认证。 正式后台需要登录、RBAC、操作审计、case 分配和 reviewer 身份。
Gmail app password 做 live demo。 生产用正式邮箱/WhatsApp Business API，凭据托管在 secret manager。
规则 YAML 手工维护。 规则包版本、effective date、GOV.UK 监控、变更 review 流程。
LLM fallback 简化。 模型网关、超时预算、重试策略、敏感信息 redaction、成本监控、provider fallback。
整案分析层默认使用 deterministic fallback；真实 LLM adapter 是 opt-in smoke path。 建立整案分析评测集、模型版本回归、提示注入防护、adviser 采纳/驳回闭环和责任归属。
PDF report 用无依赖简版渲染。 正式 PDF 模板、品牌样式、分页、附件索引、签名/版本号。
PoC 产品类型是 UK Standard Visitor，但只完整覆盖探亲 reference scenario。 已有 route registry 和组件化 rule pack；旅游、短期商务等目的继续补 verified purpose pack、测试夹具和人工审核 SOP。
生产环境最重要的不是“把模型换成更强的”，而是把责任边界做清楚： 哪些内容由系统检查，哪些内容由人工顾问签字，哪些内容必须由申请人确认。

8. 演示时怎么讲

  1. 先讲业务代价不对称，所以不能让 LLM 自由判断。
  2. 展示一封新客户邮件如何创建 case，并通过自然语言 intake 填 slots。
  3. 展示材料清单来自规则配置，不是模型编的。
  4. 上传一批附件，说明 OCR/LLM 只抽字段，validator 才判断通过/失败。
  5. 展示失败材料补件、重复邮件去重、跨文件重检。
  6. 展示整案分析：当前 fallback 对长停留、资金接近行程成本、英国定居亲属生成观察，并展示 evidence refs。
  7. 说明可选 LLM candidate 接口已经有引用护栏，但 live model adapter 仍是下一步，不把 seam 当成已上线能力。
  8. 进入 admin panel，说明 human review gate 和 adviser 对整案观察的最终责任。
  9. approve 后发 final package：PDF/HTML report + accepted 原文件。
  10. 最后讲 production TODO：数据保护、权限、规则 freshness、模型可观测性、人工责任。
