## 0. 结论先说

1. **范围定在访客签证（Standard Visitor），演示场景用"探亲 + 英国亲属担保"。** 它是唯一没有第三方前置文件依赖的类别，两天能端到端跑通；而它的核心审查标准是主观判断题，正好能区分"顾问"和"填表机器"。
2. **交付稳定性的答案不是"把提示词写好"，是把不该交给模型的东西全部拿走。** 状态外置、规则外置、输出模板化、断言可溯源、不下结论、人工关口——六条，见第 4 节。
3. **架构是"流程为骨架、模型为器官"，不是纯 agent。** 判断依据是三个问题（输出空间是否有限、错误是否可逆、是否需要可复现），逐环节结论见第 5 节。

一句话概括这套方案的立场：**这门生意的失败代价高度不对称——多问客户一句只是啰嗦，漏一份材料是拒签、£135 不退、行程报废、还会留下拒签记录影响以后申请。不对称的代价必须由确定性结构兜底，模型只在它确有优势的地方介入。**

## 1. 范围选择

### 1.1 为什么是访客签证

| 类别 | 前置依赖 | 两天可行性 | 顾问价值 | 判断 |
|---|---|---|---|---|
| 访客签证 Standard Visitor | 无 | 高 | 高（主观审查） | **选它** |
| 学生签 Student | 学校签发 CAS | 低 | 中 | 排除 |
| 工签 Skilled Worker | 雇主签发 CoS + 担保牌照 | 低 | 中 | 排除 |
| 配偶 / 伴侣 Appendix FM | 无，但举证极重 | 低 | 极高 | 排除 |

学生签和工签都卡在一份由第三方机构签发的前置文件上，agent 既拿不到也造不出来，演示会在第一步就断掉。学生签的规则其实最好校验（全是客观条件），但可跑通性对两天的 demo 更重要。

配偶签顾问价值最高，但两天做不完，且涉及收入门槛和关系真实性举证，做错对客户的伤害远大于一次访客签拒签。

访客签的好处是闭环短：申请人自己手上的材料就构成完整一套。同时它的审查标准恰好"没有硬指标、全靠综合判断"，这正是人类顾问在做的事。

### 1.2 演示场景

**探亲访问 + 英国定居亲属担保。** 这是访客签里最容易被拒的情形——申请人在英国有定居亲属，签证官会把这当成滞留动机，需要顾问主动补强反向证据。

具体客户画像（故意带弱点）：**自由职业、资金刚够、姐姐已在英国定居、想住三个月。**

看点是 **agent 能不能自己识别出这一组风险并主动要求补强**，而不是照单收材料。如果只演示"有稳定工作、去伦敦玩一周"，看不出和填表工具的区别。

## 2. 业务底层（配菜，够用即可）

### 2.1 三层结构

访客规则在《移民规则》Appendix V：**Validity**（V2，形式关：在线申请、缴费、生物信息）→ **Suitability**（V3，Part 9 一般拒签理由）→ **Eligibility**（V4 起，核心）。

### 2.2 真实访客测试（V 4.2）——整个业务的重心

申请人必须让签证官相信四件事：

- (a) 会在访问结束时离开英国；
- (b) 不会通过频繁或连续入境长期居留，或把英国变成主要居所；
- (c) 确实为规则允许的目的入境；
- (d) 有足够资金覆盖此行全部合理费用，无需工作也无需动用公共福利。

**签证官不满意就必须拒签，没有酌情空间。** (a) 是最常见的拒签原因。

### 2.3 签证官实际权衡的因素

来自内政部对内的《Visit caseworker guidance》（2026-02 更新）。这份材料最有价值，因为它写的是审查逻辑而非申请须知：

- 以往出入境记录（含去英国和其他国家的记录）；
- 以往访问的停留时长，是否明显超过当初申报；
- 财务状况，以及家庭、社会、经济背景；
- 与常住国之间的个人和经济联系；
- 最近 12 个月累计在英停留时间和出行模式。

**明确列出的疑点信号**：在常住国几乎没有家庭和经济联系却在英国有多名亲属；申请人与担保人陈述矛盾；信息经核查无法验证。

### 2.4 资金要求（对设计有直接影响）

**没有法定最低金额。** 判断标准是收入扣掉固定支出后能否合理覆盖此行开销。

> **这一条直接决定了一个设计决定**：代码里不能写死任何金额门槛，模型也不能判定"够不够"。系统只做一件事——**把客户资金和行程开销的比较结果摆出来给人看**。这是第 4 节"不下结论"那条防线在业务上的来源。

第三方出资允许，但出资人须与申请人有真实的职业或私人关系。签证官会查关系真实性、担保人以往担保记录、担保人的钱够不够同时养自己和申请人。

### 2.5 材料清单（实务）

护照及既往签证页；近 6 个月银行流水；在职证明、准假信、工资单（自雇则为营业执照、完税记录）；住宿证明；往返行程；与常住国联系的证据（房产、社保、在读子女、赡养责任）；担保人材料（担保信、身份或居留证明、流水、住址证明）；非英文材料的认证翻译件。

其他事实：可提前 3 个月申请；每位家庭成员各自申请各自缴费；六个月访客签 £135；递交生物信息后通常 3 周内出结果。

### 2.6 拒签高发人群

自由职业或非正规就业、刚换工作或待业、新近自雇、主要依靠英国亲属出资、常住国联系薄弱、英国有定居直系亲属。**这几类恰恰是最需要顾问的客户**，所以演示客户就该从这里挑。

## 3. 顾问工作流、渠道分工、交付物

### 3.1 把顾问的工作拆开

| 阶段 | 顾问在做什么 | 产出 |
|---|---|---|
| 1 资格初筛 | 确认是否需要签证还是 ETA、目的是否属允许范围、时间来不来得及 | 接不接这个案子 |
| 2 案情画像 | 问出职业、收入、资金、家庭、出行史、担保人情况 | 结构化案情档案 |
| 3 风险诊断 | 对照真实访客测试，找出薄弱点 | 风险清单 + 补强方向 |
| 4 清单定制与收集 | 给出针对性清单，反复催收 | 材料齐了 |
| 5 材料质检 | 完整性、一致性、时效性、可读性、翻译 | 退回重做或通过 |
| 6 组稿交付 | 表格答案、说明信、打包 | 交付物 |

第 3 步是顾问真正值钱的地方，也是 agent 最该证明自己的地方。第 4 步占掉顾问最多时间，是效率收益的主要来源。

### 3.2 两个渠道各干什么

不是"两个渠道都能聊天"，而是物理特性不同：

- **WhatsApp** —— 低摩擦、高频、移动端。用于初筛问答、案情访谈、催收提醒、拍照上传、进度通知。
- **邮件** —— 结构化、可存档、能带附件和长文档。用于正式清单、质检报告、最终交付包。

原则：**对话走 WhatsApp，文档走邮件。** 客户不会在 WhatsApp 里认真读 20 项清单，也不会在邮件里一天回你八次。

### 3.3 WhatsApp 的硬约束（影响流程设计）

- 客户发来消息开启 **24 小时会话窗口**，窗口内可自由发送；客户再次发消息重置计时。
- **窗口关闭后只能发 Meta 预审过的模板消息。** 所以催收不能想发就发，必须设计成有限次数的模板推送，模板要提前报审。
- **2026-10-01 起计费变更**：原本窗口内免费的服务消息和实用类模板将按条计费。催收节奏会直接变成钱。

### 3.4 交付物定义

1. **个性化材料清单** —— 每项标注：为什么需要（指回规则或风险点）、什么格式、已收到还是待补。
2. **申请表答案草稿** —— 客户需填入 GOV.UK 在线表格的关键答案。
3. **说明信（cover letter）草稿** —— 把客户情况与真实访客测试逐条对应，重点解释弱点。
4. **质检报告** —— 哪些材料有问题、为什么、怎么改。

**交付边界**：英国内政部没有对第三方开放的申请提交接口，正式申请只能由申请人自己走 GOV.UK，生物信息另走签证中心。所以"自动提交"不是砍掉的功能，而是长期都接不上的一步。**产品天花板就是交出一套齐备、已校验的材料包。**

## 4. AI 交付稳定性（主菜一）

### 4.1 这个领域真正的失败模式

不是"回答得不够好"，是下面这些。把失败模式列清楚是设计的前提——**防线是逐条对着失败模式建的**：

| # | 失败模式 | 后果 |
|---|---|---|
| 1 | 规则过时（费用、政策、表格会变） | 给出错误要求 |
| 2 | 凭空编出要求，或漏掉必需项 | 漏项直接导致拒签 |
| 3 | 替客户下"够不够"的结论 | 无法验证，错了代价是拒签 |
| 4 | **诱导或默许造假** | **最重**：强制拒签，故意欺骗触发 10 年入境禁令 |
| 5 | 长对话状态丢失（信息散在几十条消息里） | 前后矛盾、重复索要、遗漏 |
| 6 | 跨渠道身份错配（WhatsApp 号与邮箱对不上） | 材料串案 |

关于第 4 条需要展开，因为它是这道题里最值得写的风险：移民规则 9.7.1 规定虚假陈述属**强制拒签、无酌情空间**，即使非故意也会导致拒签；被认定故意欺骗的，触发 **10 年入境禁令**，且从使用欺骗之日起算。而大模型的默认倾向恰恰是"帮客户把案子写得好看一点"——修饰资金来源、圆一个行程、美化在职证明。**这必须在架构层面阻断，只在提示词里写一句"不要造假"是不够的。**

### 4.2 六道防线

1. **状态外置。** 案情档案是唯一真相源，固定 schema 存 DB。模型每轮从它读、往它写，不依赖对话历史。→ 解决 5、6。
2. **规则外置。** 材料清单和判定规则做成带**生效日期 + 来源链接**的版本化配置，不写进提示词。规则变更只改数据，不用赌提示词。→ 解决 1。
3. **输出受限。** 交付物用模板渲染，模型只填字段。**清单绝不由模型即兴生成**，必须从画像按规则映射。→ 解决 2。
4. **断言可溯源。** 每一句"你需要 X"都要能指回具体规则条目。指不回去的不许进交付物。→ 解决 2、3。
5. **不下"够不够"的结论。**（@Ian 提出，比我第一版的写法更严）真实访客测试没有硬标准，"你的离境意图证据够了"这类判断既无法验证、错了代价又是拒签。
   - **允许**：按项检查有没有、齐不齐，把缺口讲清楚。
   - **禁止**：成功率预测、"这样就能过"、任何强度评估。
   - **强度评估交给人。** agent 产出"证据齐备度 + 已识别风险点"，人类顾问定调。
   - 这条同时兼容 2.4 的业务事实（没有法定资金门槛）——不是我们保守，是规则本身就没有可判定的线。
6. **事实只出自客户。** agent 只能引用客户提供的事实，不能生成或修改任何事实性内容。说明信可以**解释和组织**事实，不能**创造**事实。做成独立的输出检查，不是提示词里的一句话。→ 解决 4。

### 4.3 怎么证明它是稳的（这一节是答题的关键）

"设计得稳"和"证明它稳"是两回事。三种可做的验证：

1. **可复现性测试** —— 同一份案情档案重复跑 N 次，生成的材料清单必须逐项一致。清单由规则映射产生而非模型生成，所以这个测试**应当**通过；一旦不通过，说明有逻辑漏进了模型侧。这是架构选择的自检。
2. **对抗用例集** —— 针对每条失败模式各准备几个用例：
   - 客户提供前后矛盾的信息（收入与流水对不上）；
   - 客户漏答、答非所问、一句话里塞四个信息；
   - **客户主动要求造假**（"能不能把流水写得好看点""就说我是公司员工吧"）——必须稳定拒绝并给出合规替代路径；
   - **诱导 agent 下结论**（"你就说我能不能过吧"）——必须稳定不接。
3. **溯源覆盖率** —— 统计交付物里有多少条断言能指回规则条目。目标是 100%，指不回去的条目本身就是 bug 报告。

> 面试角度：第 2、3 条是能直接演示的，比任何论述都有说服力。

### 4.4 关于合规（刻意压缩）

第一版这里是一整节。现在明确是笔试题，产品定位不是考点，所以压缩成三句：

- 英国的移民建议是持牌行业（1999 年《移民与庇护法》第 82 条），未持牌在英国境内以经营方式向特定个人提供移民建议是刑事犯罪，免费也算。监管机构 OISC 已于 2025-01 更名 Immigration Advice Authority。
- 监管指引的界线是：可以准备材料、可以建议"哪类证据适合"；**不可以协助填写申请表，不可以判断材料或情况是否满足申请要求。**
- **值得注意的是这条法律界线和 4.2 第 5 条防线是同一条。** 所以"不下结论"和"人工复核关口"这两个设计不依赖持牌与否成立——它们本来就是可靠性设计，合规只是又一次指向同一个答案。

## 5. Agent 还是 Workflow（主菜二）

### 5.1 判断依据

不按"哪个更时髦"选，按三个问题逐环节问：

1. **这一步的输出空间是否有限？** 有限 → 规则能穷举 → workflow。
2. **这一步出错是否可逆？** 不可逆或代价高 → workflow。
3. **这一步是否需要可复现？** 需要审计、需要同样输入得同样输出 → workflow。

三个都是"否"，且需要理解自然语言或生成自然语言 → 才轮到模型。

### 5.2 逐环节结论

| 环节 | 选择 | 理由 |
|---|---|---|
| 资格初筛 | **Workflow** | 决策树，规则明确，必须可复现 |
| 案情画像 | **Agent** | 客户答非所问、信息零散、需要追问，自然语言的主场 |
| 风险诊断 | **Agent + 规则校验** | 模型识别风险点并说明缺口，但不下"够不够"的结论（4.2 第 5 条） |
| 清单生成 | **Workflow** | 从画像映射到清单是纯规则。**绝不让模型自由发挥**，漏项代价太大 |
| 收集催收 | **Workflow** | 状态机 + 定时，还受 WhatsApp 模板和窗口约束 |
| 材料质检 | **混合** | 格式、时效、完整性用规则；内容一致性（流水与在职证明对不对得上）用模型 |
| 说明信起草 | **Agent + 模板约束 + 人审** | 需要语言能力，但必须锁住结构和事实边界 |
| 提交申请 | **不做** | 没有接口，且是风险集中点 |

### 5.3 落地形态

**显式状态机驱动整体推进**：`意向采集 → 场景判定 → 生成清单 → 逐项收证 → 校验 → 补件 → 组装交付包 → 人工复核`。

- 案件状态存 DB，不存在模型上下文里。
- 每个状态下调用受限的模型完成局部任务，输入输出都过 schema 校验。
- **状态转移由代码判断，不由模型决定。** 这是整个架构最关键的一句。
- 推导下一步的函数应当是纯函数：同样的案件状态永远推导出同样的下一步。

反过来说，**纯 workflow 也不行**——客户在 WhatsApp 上不会按表单顺序说话。"我表姐在曼城，我想去看看她，大概待仨月吧"这一句里同时藏着目的、担保人、时长和一个风险点，这个必须靠模型拆。

### 5.4 什么情况下我会改主意

（写这一段是因为笔试里"我的结论在什么条件下不成立"通常比结论本身更值分。）

上面的配比是被**高错误代价 + 低规则变化率**这两个条件推出来的。如果条件变了：

- **错误代价变低**（比如产品退回到"签证咨询问答"而不是"带客户备料"）→ agent 比例可以大幅上升，因为答错一句的代价只是重问一次。
- **需求长尾变宽**（比如要同时覆盖十几个签证类别和大量边缘情形）→ 穷举规则的成本会超过收益，这时该把更多判断交给模型，用检索给它喂规则原文。
- **规则变化极快** → 规则外置的收益进一步放大，但清单生成仍应保持确定性，只是配置更新更频繁。

**不会改变的是第 4.2 节的六条防线**——它们跟 agent / workflow 的配比无关，是这个业务本身的要求。

---

## 6. 两天怎么切

**第一天**：案情档案 schema、规则与清单配置（只覆盖探亲访问这一条分支）、WhatsApp 接入（用 sandbox 或模拟，不等正式账号审核）、初筛与画像。

**第二天**：风险诊断、清单生成、催收状态机、邮件交付物渲染、人审步骤、对抗用例集、演示脚本走查。

**说明信的优先级**：先跑通"清单 + 催收 + 质检"闭环，说明信做模板版。理由是依赖关系而非偏好——闭环建好之后模板版说明信几乎白送，反过来不成立；而且在"事实只出自客户"这道校验建好之前就去做最容易编造的那个产物，顺序是反的。（此结论采纳 @Ian 的判断，我原本主张相反。）

---

## 7. 明确不做，以及为什么

笔试里"我为什么没做 X"和"我做了什么"一样值分。

| 不做 | 原因 |
|---|---|
| 自动提交申请 | 内政部没有第三方接口，绕过既违反使用条款也踩监管线 |
| 多签证类别 | 两天做不完；且会稀释"闭环跑通"这个更重要的证明 |
| 正式 WhatsApp Business API 账号与模板报审 | 审核周期不可控，PoC 用模拟即可，不影响架构验证 |
| 成功率预测 / "你能不能过" | 见 4.2 第 5 条，这是设计立场不是能力不足 |
| 多语言、支付、账号体系 | 与两个考点无关 |
| 真实客户数据 | 护照和流水是高敏感个人资料，PoC 一律用构造数据 |

## 8. 上生产还欠什么

1. **责任主体**：IAA 注册，或与持牌顾问机构合作并明确权责划分。
2. **数据合规**：护照、银行流水属高敏感个人数据，需按 UK GDPR 处理——加密存储、留存期限、数据处理协议、跨境传输机制。**真实客户进来之前必须做完。**
3. **WhatsApp 正式化**：Business API 账号、模板报审、2026-10-01 计费变更的成本重算。
4. **规则更新机制**：监控 GOV.UK 变更，规则配置带版本和生效日期。
5. **审计日志**：每条给客户的建议可追溯到当时的规则版本和人审记录。出纠纷时这是唯一的自证材料。
6. **拒签复盘闭环**：拒签信里的理由回流到规则和风险模型——这是产品长期变强的唯一途径。
7. **反欺诈**：客户提交伪造材料时的识别与拒接机制。
